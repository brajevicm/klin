# File length and function count per file, 2026-10-10

This note belongs to #610. It asks if klin should hold the size of a source
file as a ratchet, and if so, which measure and which shape.

It is research only. It adds no gate, changes no shipped behavior and edits no
SPEC semantics. A disposition here does not authorize an implementation: that
is a separate ticket after a person reviews this note.

## Terms

These words are local to this note. They are not terms of `CONTEXT.md`:

- A **metric** is one size measure of one file.
- A **system** is one repository of the corpus at one commit.
- A **relative threshold** `(p, k)` says that p% of the files of a system have
  a metric value of k or less (Oliveira, Valente, Lima, CSMR-WCRE 2014).
- A **compliant system** is a system that meets a relative threshold.
- **`sizes`** is the throwaway prototype that measures every metric,
  `docs/file-size-2026-10-10/prototype/`. It is not klin code. It uses the
  tree-sitter grammars klin pins (`Cargo.toml`), and it counts functions with
  the node kinds of `src/syntax/mod.rs`.

## Rules, written before any run on the corpus

The commit that adds this section holds no result of either corpus. The
prototype ran before this commit only on klin's own tree, to find parser
mistakes.

### Languages and files

Rust (`.rs`), TypeScript (`.ts`, `.mts`, `.cts`) and TSX (`.tsx`). A `.d.ts`
file is out of scope, because it declares and holds no code. Like klin, the
prototype skips every directory of `DEFAULT_SKIP_DIRS` in
`src/facts/files.rs` and every hidden directory. It reads the blobs of one
commit through `git cat-file`, so a result does not depend on a checkout.

A file is a **test file** when a directory segment of its path is in
`TEST_DIRS`, or its basename carries a test affix of `src/facts/survey.rs`.
A file is **generated** when one of its first ten lines holds `@generated`,
`do not edit`, `auto-generated`, `autogenerated`, `automatically generated`
or `code generated by`, case-insensitively. This is a heuristic. klin has no
such rule (ADR 0003 and #500 never drop a file for its content).

### Metrics

| Metric | Definition |
| --- | --- |
| `lines` | Physical lines. A last line with no newline counts. |
| `code` | Lines that hold at least one token outside a comment. A multi-line string counts each of its lines. |
| `items` | Top-level declarations. Rust: the named children of `source_file`, less `use`, `extern crate`, attributes, comments and a `mod x;` with no body. TypeScript: the named children of `program`, less imports, comments and re-exports (`export … from`, `export { … }`). |
| `functions` | Every node of the language's function kinds in `src/syntax/mod.rs`. For TypeScript this counts every arrow function and callback, as `complexity` does. |
| `named` | Rust: every `function_item`. TypeScript: function and generator declarations, methods, and an arrow function or function expression that is the value of a variable declarator or a class field. |
| `production` | `named`, less the functions of a test file, a Rust `#[test]`-style function, and a function inside a Rust `#[cfg(test)]` module. |

`longest` (the longest production function, in lines) is recorded only to
compare with `complexity`. It is not a candidate.

### Corpus A: distribution

1. Two GitHub searches, run once and kept as they came:
   `language:Rust stars:>1000 pushed:>2026-09-01 size:<200000 fork:false` and
   the same with `language:TypeScript`, each sorted by stars, descending, 100
   results per page, first page only.
2. Walk each list in its order. A repository is eligible when all of these
   hold:
   - A clone of depth 1 of its default branch finishes.
   - The commit holds `Cargo.toml` at the root for Rust, or `package.json` at
     the root for TypeScript.
   - The commit holds at least 50 files of the language that are neither test
     files nor generated.
3. Take the first 50 eligible repositories of each list. Record every
   repository skipped before them, with the rule it failed.
4. The selection, with each commit id, is frozen in `selection.json`.

A system's files are its files of the list's language. A Rust repository's
TypeScript files are out of its system, and the reverse.

### Corpus B: windows

The ten repositories and 100 changes of #343
(`benchmark/evidence/false-alarms-2026-09-29/selection.json`). Their
`klin gate --json` output with `{}` is already in that directory, so the
overlap with `complexity` reads recorded findings and needs no new klin run.

### Analysis

For each language and metric, over production files (neither test nor
generated) unless a row says otherwise:

1. The pooled percentiles 50, 70, 75, 80, 90, 95 and 99, and the share of all
   lines that the largest 10% of files hold.
2. The relative threshold by Oliveira's method, with their parameters: Min
   90, Tail 90, p in {75, 80, 85, 90, 95}, k every whole number from 1 to
   the largest value in the corpus. The pair with the lowest penalty wins.
   Ties go to the highest p, then the lowest k. The result lists the
   non-compliant systems.
3. The Spearman correlation between each pair of metrics over all files, to
   show which metrics measure the same thing.
4. Stability of a derived ceiling: for each repository of corpus B, the 95th
   percentile of each metric at the start commit and at the first-parent
   commit 500 commits before it, or the root commit if the walk is shorter.
5. For corpus B, per change: the files whose metric grew, and the files that a
   ratchet with the repository's derived ceiling (95th percentile at the
   change's base, rounded up) would find. A file is found when its value at
   the head is over the ceiling and it is new, or it grew. This is the same
   rule `complexity` uses for a function (SPEC 8.2.1).
6. For each file found in step 5: whether the recorded `complexity` run of the
   same change failed on a function in that file.
7. One label per file found in step 5, by reading the change:
   - `split` when a split along a seam the file already shows (two types, two
     concerns, a table apart from its logic) would read better;
   - `cohesive` when the file is one concern that grew, and a split would only
     move the number;
   - `generated`, `table` or `test` when the file is one of those kinds that
     the heuristics missed.
   The labels are agent-drafted.

### Outcomes

Each metric ends with one outcome:

- **BLOCK candidate** when all of these hold: the metric finds files in at
  most 10 of the 100 changes; at least 80% of its findings are `split`; at most
  half of its findings are on files that `complexity` already failed in the
  same change; and no appeasement in section 5 satisfies it at a cost below a
  real split.
- **REVIEW candidate** when the first three hold and an appeasement exists.
- **NOTE only** when the metric adds information that the other gates lack but
  fails a REVIEW rule.
- **reject** otherwise.

A BLOCK or REVIEW candidate gets an agent repair experiment before this note
recommends it. A metric with no such outcome needs none.

### Stop-path cost

`sizes time` on the clone of the largest repository per language, three runs,
for the whole tree (a derivation) and for 20 changed files (a warm Stop).

## Deviations from the rules

Each change below came after a corpus run. The note marks every result it
affects.

1. **A post-hoc metric, `prodcode`.** The first Rust results counted inline
   `#[cfg(test)]` modules as file lines. In `pdf-inspector`,
   `src/extractor/content_stream.rs` has 5,767 lines and 2,425 of its code
   lines are outside tests. `prodcode` is `code` less the lines of a Rust
   `#[test]`-style function and of a `#[cfg(test)]` module. For TypeScript it
   equals `code`, because a test file is never a production file.
2. **The Spearman correlations use production files only**, not all files.
   The rules said all files.
3. **No macOS `timeout`.** The first selection run failed every clone,
   because macOS has no `timeout` command. `corpus/select.sh` uses a `perl`
   alarm of 600 seconds. The second run is the one recorded.

## How to reproduce

`docs/file-size-2026-10-10/` holds the corpus and the scripts:

- `prototype/` builds `sizes`. `sizes scan REPO REV` prints one row per file,
  `sizes change REPO BASE HEAD` prints the changed files at both sides.
- `corpus/search-*.json` are the two search responses of 2026-10-10.
  `corpus/select.sh SIZES CLONES` replays the selection and writes
  `selection.json` and `skipped.tsv`.
- `analyze.py SIZES CLONES` writes `results/corpus-a.json`.
- `windows.py SIZES FULL_CLONES` writes `results/windows.tsv`,
  `results/growth.tsv` and `results/stability.tsv` for corpus B.
- `results/labels.tsv` holds one label per file that corpus B found.
- `appease.sh SIZES ARNIS_CLONE WORKDIR` builds the appeasement branches of
  section 3 and prints their metrics.

For comparison, Oliveira et al. found 75% ≤ 222 LOC and 80% ≤ 16 methods per
Java class on 106 systems. TypeScript files are in the same range for lines
(263 code lines). They hold fewer named functions (10), because a TypeScript
file holds more top-level code and callbacks than a Java class. Rust files are
about twice as long (492 code lines outside tests) and hold more functions
(25 outside tests).

The method gives one number per corpus. It says that most files of most
systems stay under it. It does not say a file over it is worse. These are
descriptive numbers, not a reading of cognitive load.

### What the metrics measure

Spearman correlations over production files:

| Pair | Rust | TypeScript |
| --- | --- | --- |
| `lines` ~ `code` | 0.99 | 0.98 |
| `code` ~ `prodcode` | 0.94 | 1.00 |
| `lines` ~ `named` | 0.86 | 0.70 |
| `lines` ~ `items` | 0.79 | 0.69 |
| `named` ~ `production` | 0.94 | 1.00 |
| `prodcode` ~ `longest` | 0.80 | 0.78 |

`lines` and `code` measure the same thing. A function count and a line count
agree less in TypeScript, where a file of a few long components and a file of
many small helpers have the same length. `longest`, the length of the longest
function, correlates with file length at 0.78 to 0.80. A long file usually
holds a long function, which `complexity` already judges.

In mature repositories the derived ceiling holds within about 20%. In young
repositories it rises as the large files grow, by four to five times in
`arnis` and two times in `pdf-inspector`. Across corpus A, the per-system 95th
percentile of `lines` runs from 181 to 11,159 in Rust (median 1,231) and from
204 to 1,373 in TypeScript (median 573). A per-repository derived ceiling
therefore holds a repository to its own largest files. In a repository of
5,000-line files it is 5,000 lines.

### Windows (corpus B)

A file is found when it is over the change's derived ceiling at the head and it
is new or grew. Over production files:

| Metric | Changes with a finding | Findings | `split` | `cohesive` | `table` | `test` | Same file failed `complexity` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `lines` | 21 | 40 | 22 (55%) | 18 | 0 | 0 | 23 (58%) |
| `code` | 21 | 38 | 19 (50%) | 17 | 2 | 0 | 23 (61%) |
| `prodcode` (post-hoc) | 18 | 34 | 15 (44%) | 16 | 3 | 0 | 22 (65%) |
| `items` | 16 | 21 | 13 (62%) | 3 | 4 | 1 | 14 (67%) |
| `functions` | 22 | 55 | 21 (38%) | 18 | 1 | 15 | 29 (53%) |
| `named` | 20 | 35 | 20 (57%) | 15 | 0 | 0 | 21 (60%) |
| `production` | 17 | 29 | 15 (52%) | 14 | 0 | 0 | 18 (62%) |

Three facts explain most of the table:

1. **The same large files fire again and again.** Of the 40 `lines` findings,
   33 are files that were already over the ceiling at the base. Changes go
   where the code is, so a ratchet on file size fires on every change that
   adds a line to a hot file. The median growth that fired was 44 lines and
   the smallest was 1 line.
2. **Most findings overlap `complexity`.** In 53% to 67% of findings, the
   same change also failed `complexity` on a function in the same file.
3. **Half the large files are one concern that grew.** A file that is one
   class (`ApolloClient.ts`, `ObservableQuery.ts`, `QueryManager.ts`), one
   editor type (`arnis` `world_editor/mod.rs`) or one service
   (`qinglong` `cron.ts`) is labeled `cohesive`. A split moves the number and
   adds an interface, which Ousterhout's "classitis" warns against.

`functions`, which counts every arrow function, finds 15 new type-test files
in `apollo-client` under `integration-tests/`, a directory the test rules do
not name. The callbacks of `test(...)` count as functions.

What file size adds beyond `complexity`: of the 40 `lines` findings, 17 are on
files where `complexity` did not fail, and 7 of those are `split`. Across 100
changes, that is 7 findings that only a file-size measure would raise and that
a reader would agree with.

## 3. Appeasement

`highways.rs` from `louis-e/arnis` at `daee5a7bff24` has 4,379 lines against
a ceiling of 2,550. Three changes each satisfy a file-size ratchet:

| Change | `lines` | `code` | `named` | `longest` | Cost |
| --- | --- | --- | --- | --- | --- |
| None (base) | 4,379 | 3,587 | 103 | 1,000 | |
| Cut at the first item past the middle into `highways2.rs` | 2,271 + 2,108 | 1,811 + 1,776 | 36 + 67 | 1,000 | a `mod` line and imports |
| Move to `src/fixtures/highways.rs` | not measured | | | | a path in the `mod` line |
| Join short lines where no comment or string is near | 1,963 | 1,264 | 103 | 441 | none, the file still parses |

The cut picks no seam. It satisfies every metric, because each half is under
the ceiling. A file-size gate cannot tell this cut from a split along a real
seam, since both produce two smaller files. Only the review of the split can.

Moving a file into a skipped directory hides it from every check. #523
already makes klin report a source file that moves into a skipped directory
as a review item.

Joining lines satisfies `lines` and `code`. A formatter reverses it, and klin
does not run one. `items` and the function counts resist joining, because they
count declarations. They yield to the cut, and to inlining: three helpers
inlined into their caller lower `named` by three and raise `longest`, which
`complexity` then judges.

The repair this gate asks for, a split, is the appeasement too. That is the
difference from `complexity`, whose advice also asks for a split but measures
the function that the split must change.

## 4. Outcomes

Every metric fails the BLOCK and REVIEW rules on all three counts that the
rules fixed before the run: each finds files in 16 to 22 of the 100 changes
(the limit is 10), at most 62% of each metric's findings are `split` (the
limit is 80%), and more than half of each metric's findings are on files that
`complexity` already failed (the limit is half).

Each metric still raises some `split` findings that `complexity` does not, so
each meets the NOTE rule.

| Metric | Outcome | Reason |
| --- | --- | --- |
| `lines` | NOTE only | 21 changes, 55% `split`, 58% overlap |
| `code` | NOTE only | Same as `lines` (ρ 0.98–0.99); gives nothing beyond it |
| `prodcode` | NOTE only (post-hoc) | 18 changes, 44% `split`, 65% overlap; the fairest Rust length |
| `items` | NOTE only | 16 changes, 62% `split`, 67% overlap; resists joining lines |
| `functions` | NOTE only | 22 changes, 38% `split`; counts callbacks and type tests |
| `named` | NOTE only | 20 changes, 57% `split`, 60% overlap |
| `production` | NOTE only | 17 changes, 52% `split`, 62% overlap |

No metric reached BLOCK or REVIEW, so the rules call for no agent repair
experiment. None ran.

## 5. Recommendation

1. **Do not add a file-size gate.** No metric is precise enough to hold the
   loop, and the repair it asks for is also its cheapest appeasement.
2. **If klin ever shows file size, show one metric as a NOTE**, `prodcode`
   for Rust and `code` for TypeScript (they are the same measure for
   TypeScript). The other metrics add nothing: `lines` and `code` correlate at
   0.98 or more, and the function counts trade noise from callbacks and test
   files for resistance to joined lines.
3. **Use a relative threshold, not the per-repository 95th percentile.** The
   derived p95 holds a repository to its own largest files, from 181 to 11,159
   lines across corpus A, and it rises in a young repository. The corpus
   numbers of section 2 (Rust 75% ≤ 492 code lines outside tests, TypeScript
   75% ≤ 263 code lines) are a fixed, cited reference.
4. **Tell it once per file.** 33 of 40 findings were files already over the
   ceiling. A note on every change to a hot file is noise. A note when a file
   first crosses the threshold is information.

## 6. Smallest implementation boundary, if a NOTE is admitted later

- Inputs: the file's text and the comment and test ranges the structural pass
  already reads. No new parse.
- Identity: the file path. A file has one size, so no site key is needed.
- Window: a file that crosses the threshold in the window, measured at both
  sides as `complexity` measures a function (SPEC 8.2.1, ADR 0001).
- Output: one NOTE line naming the file, its code lines and the threshold.
  Never FAIL, never in the block budget.

## 7. Interaction with existing gates

- **`complexity`** already judges the function that most large files hold. It
  overlapped 53% to 67% of the findings here. A file-size NOTE adds the files
  whose size is many small functions.
- **The skip set** gives every check the same move-to-a-skipped-directory
  route, and #523 already reports that move. A file-size measure adds no new
  hole and closes none.
- **`doc-size`** measures agent documents, not source. Nothing in this note
  changes it.
- **ADR 0067** lays out klin's own `src/` by component. It is a structure
  rule, not a size rule, and it is the kind of decision that a file-size
  number cannot make.

## 8. SPEC language this result requires

None. This note admits no gate. If a person admits the NOTE of section 6, the
SPEC needs a check row (`file-size`, NOTE only, never blocks), the metric
definition of `prodcode`, the threshold source (this note's corpus and
Oliveira's method), and the told-once rule.

## Stop-path cost

`sizes` re-parses every file. On the clone of the largest repository per
language, three runs each:

| Repository | Files | Whole tree |
| --- | --- | --- |
| gfx-rs/wgpu (Rust) | 857 | 1,122–1,136 ms |
| refactoringhq/tolaria (TypeScript) | 1,715 | 1,231–1,280 ms |

A change of 39 Rust files in `wgpu`, both sides, took 480–500 ms. klin already
parses the changed files for `complexity` and holds their function spans, so
the marginal cost inside klin is counting rows. This is an inference: no klin
run measured it.

## Limits

- The labels are agent-drafted from each file's outline, not from a full
  read. A person may move several `cohesive` files to `split` or back. The
  outcomes hold even if every `cohesive` label flips to `split`, because the
  frequency rule fails alone (16 to 22 changes against a limit of 10).
- The corpora are popular open-source repositories. They say what is common,
  not what is readable, and nothing about how agents grow files.
- The test and generated rules are heuristics. `apollo-client`'s
  `integration-tests/` shows a test directory they miss.
- Corpus B is 100 changes. The frequency of findings may differ in a repository
  with smaller files.
